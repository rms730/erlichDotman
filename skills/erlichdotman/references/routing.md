# Routing

Tier 0 resolves uncertainty with tools and no inference. Tier 1 fits specified mechanical work. Tier 2 fits ordinary implementation and review. Tier 3 fits architecture, unfamiliar systems and difficult debugging. Tier 4 fits critical/irreversible decisions where additional reasoning may increase success.

Classify the next stage, not the whole project forever. Complexity, ambiguity, security, production consequences, distributed state and cross-repository dependencies justify floors. A precise implementation packet can remove ambiguity; it cannot remove the consequences of a migration. Keep risk floors after a downgrade.

The CLI's explicit bootstrap policy is uncalibrated. Select the least expensive credible method, not the cheapest nominal token price. Failed attempts, latency, attention and rework count. Only measured engineering trials can support future cost-optimized defaults.

## Configured runtime controls

Keep provider model IDs and reasoning settings in an authorized private runtime policy. Use its engineering profile by default. Its routine profile is limited to specified mechanical implementation/documentation/validation with low risk, complexity and ambiguity, no risk signals and a lightweight decision. Reserve its escalation profile for an explicit escalation stage with a defined reason or a high-risk review. A frontier decision outside those paths stops for a scope/route decision; it never silently lowers the quality floor. These role assignments are operating preferences, not measured model-quality calibration.

The policy specifies total attempts and concurrent workers. The initial example allows two total attempts and one active worker to bound retries and coordination; change limits explicitly when justified. Count completed implementation attempts, including evidence-capture retries, and all active workers in the configured host scope. Stop at the stricter routing/runtime attempt limit, the worker limit, a stop request, missing classified retry evidence, missing required facts or permission needs. Batch routine documentation at material checkpoints under the existing project-record contract.

For every policy-controlled dispatch, request explicit model/reasoning settings and require a matching host acknowledgment of selection and limit controls before launch. Recheck actual settings from host evidence when exposed. Do not fabricate an acknowledgment or infer effective settings from requested settings. An unsupported host stays blocked for this policy; an explicitly authorized manual fallback must disclose that enforcement is unavailable and is not policy-compliant execution.

The CLI's optional runtime-policy path validates bound requests and supplied acknowledgments. It launches no models, reserves no worker slots and cannot verify declarations or enforce calls made outside it. A host must perform atomic accounting and actual launch enforcement. Record observations for the exact request; retain setting mismatches as violations, missing observations as `null`, and all setup, parent, implementation, validation, review, retry and human-effort legs in private outcome evidence. Tokens do not establish billed cost; retain the applicable billing evidence and units or leave cost unknown. Core integration details remain outside the portable skill's required context.
